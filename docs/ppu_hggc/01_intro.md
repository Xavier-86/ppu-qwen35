## 1.1 PPU 并行计算与 HGGC

- **PPU（真武 PPU）**：T-Head 的并行计算处理器。**HGGC（HeteroGeneous General-purpose Computing，异构通用计算）**：T-Head SAIL 平台上的异构编程模型/软件栈总称（类比 CUDA 之于 GPU）。
- PPU vs CPU 设计目标差异：
  - CPU：追求快速执行一串串行操作（"线程"），只能并行执行**数十个**线程；晶体管更多用于**数据缓存与流控制**。
  - PPU：设计目标是并行执行**数千个**线程，**牺牲单线程性能换取极高整体吞吐量**；晶体管更多分配给**数据处理单元**。
  - 在相近成本和功耗范围内，PPU 提供远高于 CPU 的**指令吞吐量**和**内存带宽**。FPGA 能效虽高，但编程灵活性远不及 PPU。
- 利用 PPU 计算能力的途径：
  1. **本指南主线**：使用 C++ 等高级语言直接在 PPU 平台编程。
  2. **专用库**（不直接写 PPU 代码）：`acBLAS`、`acFFT`、`acDNN`、`CUTLASS` 等。T-Head 官方库已针对不同 PPU 架构专门优化，在开发效率、运行性能、代码可移植性之间取得平衡。如果库已实现所需功能，直接调用优于从零实现。
  3. **AI 软件框架**：许多框架通过调用上述 PPU 加速库实现加速。

比赛关联：Qwen3.5-2B VLM 推理中，GEMM/Attention 等成熟算子优先调用 `acBLAS`/`acDNN`/`CUTLASS`（官方已按架构优化），把自研 kernel 的精力留给融合算子（如 RMSNorm+量化、RoPE、KV cache 写入等库未覆盖的环节）。

## 1.2 HGGC 并行编程模型

本章从高层次介绍 HGGC 编程模型，**独立于任何特定语言**；术语和概念适用于所有基于 HGGC 的编程语言（后续章节用 C++ 举例）。

### 1.2.1 异构系统

- HGGC 编程模型假定一个**异构计算系统**：包含 PPU 和 CPU。
- 术语：
  - **宿主机 (host) / 宿主内存 (host memory)**：CPU 及与 CPU 直接连接的内存。
  - **设备 (device) / 设备内存 (device memory)**：PPU 及与 PPU 直接连接的内存。
- 执行模型：
  - 应用程序**始终在 CPU 上开始执行**。运行在 CPU 上的代码称为**宿主代码 (host code)**。
  - host code 通过 HGGC API：在 host memory 与 device memory 之间**复制数据**、在 PPU 上**启动代码执行**、**等待**数据复制或 PPU 代码完成。
  - 在 PPU 上执行的应用代码称为**设备代码 (device code)**；在 PPU 上调用执行的函数称为**核函数 (kernel)**（出于历史原因）；启动核函数运行的行为称为**启动 (launching)**。
  - 核函数启动 = 在 PPU 上并行执行**许多线程**运行同一份 kernel 代码。PPU 线程的操作类似 CPU 线程，但存在对正确性和性能都重要的差异（后续章节讨论）。
  - **CPU 和 PPU 可以同时执行代码**，最佳性能通常来自最大化同时利用 CPU 和 PPU。

比赛关联：TTFT 优化的基础认知——prefill 阶段 host 侧（图像预处理、tokenizer、prompt 拼接）与 device 侧（权重已驻留 device memory）应尽量重叠；数据 H2D/D2H 拷贝与 kernel 执行的流水化是降低首 token 延迟的常用手段。

## 1.3 PPU 硬件模型

HGGC 依赖底层硬件的概念模型。对 HGGC 编程而言，PPU 可视为**一系列计算单元（Compute Unit，CU）的集合**。

- 每个 CU 包含：
  - 本地寄存器文件（register file）
  - 数据缓存（Cache）
  - 共享内存（shared memory）
  - 若干用于执行计算的功能单元
- **共享内存的分配可以在运行时配置**。不同类型的内存大小和 CU 内功能单元数量**因 PPU 架构而异**。

> **NOTE**：PPU 的实际硬件布局或其物理执行编程模型的方式可能有所不同，这些差异不影响使用 HGGC 编程模型编写的软件的正确性。

### 1.3.1 线程块和网格

- 启动核函数时同时启动大量线程（通常**数百万个**），组织层级：
  - 线程 → **线程块 (thread block)** → **网格 (grid)**。
  - 网格中所有线程块具有**相同的大小和维度**。
  - 线程块和网格都可以是 **1 维、2 维或 3 维**，便于把线程映射到工作单元/数据项。
- **执行配置（execution configuration）**：启动 kernel 时指定网格和线程块维度；还可含可选参数：**集群大小（cluster size）、流 (stream)、CU 配置设置**（后续章节介绍）。
- **内置变量**：每个线程可确定：
  - 自己在所属块中的位置；
  - 其块在父级网格中的位置；
  - 启动的线程块和网格的维度。
  由此每个线程在整个启动中有**唯一标识**，常用于确定该线程负责的数据或操作。
- 调度规则（正确性关键）：
  - **一个线程块的所有线程都在单个 CU 中执行**，因此块内线程可高效通信、同步，并可访问**片上共享内存**交换信息。
  - 网格可能由数百万个线程块组成，而 PPU 可能只有几十或几百个 CU。线程块通常在所在 CU 上**运行至完成**。
  - **线程块之间的调度没有任何保证**：线程块不能依赖其他线程块的结果（其他块可能要到当前块完成后才被调度）。
  - 编程模型（有一些例外）**要求不同线程块的线程之间不存在数据依赖**：一个线程不应依赖同一网格中另一线程块线程的结果，也不应与其同步。
  - 不同线程块在可用 CU 之间调度、**可按任何顺序执行**——即 HGGC 要求线程块能以任意顺序并行或串行执行。这使任意大的网格能在任何尺寸的 PPU 上运行（一个 CU 或数十个 CU 均可）。

### 1.3.2 线程束 (Warps) 和 SIMT

- **warp 大小 = 32 线程**。线程块内的线程被组织成 32 线程一组的 warp。
- **SIMT（Single-Instruction Multiple-Threads，单指令多线程）**：warp 中所有线程执行**相同的核函数代码**，但每个线程**可沿不同分支路径**执行——线程不必遵循相同执行路径。
- **warp 通道 (warp lane)**：warp 中线程被分配到 warp lane，编号 **0 到 31**；线程块中的线程按可预测方式分配到各 warp。
- **warp 分歧 (warp divergence)**：
  - warp 中所有线程**同时执行同一条指令**；若部分线程走某分支、其他线程不走，则不走分支的线程被**屏蔽（masked）**，走分支的线程继续执行。
  - 例：条件只对 warp 中一半线程成立 → 另一半被屏蔽，活动线程执行该分支指令。
  - 结论：**当 warp 内所有线程遵循相同控制流路径时，PPU 利用率达到最大值**。
- 上下文切换：CU 的状态需要被存储到**系统管理的 PPU 内存区域**中，然后释放 CU 去执行其他线程块——类似 CPU 上的上下文切换。
- 编程纪律：
  - SIMT 模型语义上 warp 中所有线程一起逐步执行 kernel；**硬件实际执行可能不同**（硬件可透明地优化掩码通道）。**不建议利用对 warp 执行到真实硬件映射的知识**；违反模型可能导致**未定义行为**，且在不同 PPU 硬件上表现不同。
  - **线程块线程总数应指定为 32 的倍数**。任意数量都合法，但若总数不是 32 的倍数，最后一个 warp 在整个执行过程中会有未使用的 lane，导致该 warp 的功能单元利用率和内存访问不最优。
  - 理解 warp 执行模型有助于理解**全局内存合并 (global memory coalescing)** 和**共享内存 bank 访问模式 (shared memory bank access patterns)** 等概念。高级技术可通过块内 warp 专业化限制发散、最大化利用率。
- **SIMT vs SIMD**：SIMD 执行遵循单一控制流路径；SIMT 中每条线程允许独立控制流路径，因此 SIMT 不受 SIMD 那种固定数据宽度的限制。（更详细讨论见后文"线程束 (Warps) 和 SIMT"章节。）

比赛关联：写自定义 kernel（量化反量化、采样、KV cache 管理等）时：block size 取 32 的倍数；避免 warp 内分支发散（如对 batch 中变长序列做 padding 对齐）；memory coalescing 直接决定 HBM 带宽利用率——decode 阶段是访存受限的，合并访存收益最大。

## 1.4 HGGC 软硬件生态

T-Head SAIL 平台由众多软硬件组件及关键技术构成，实现异构系统上的计算能力。本章介绍对应用开发者至关重要的基本概念与核心组件，内容不局限于特定编程语言。

### 1.4.1 计算能力（Compute Capability，CC）

- 每款 PPU 都有一个"**计算能力**"（Compute Capability，CC）编号，指明该 PPU 支持的功能特性及相关硬件参数。
- 目前 PPU 支持的 ARCH 是 **`ppu_10` 和 `ppu_15`**。
- 编译时通过 **`-arch=<value>`** 形式指定；**支持多代架构的混合编译**，具体配置见 T-Head SAIL HGGC 编译文档。

### 1.4.2 SAIL 工具包与 HGGC 驱动程序

- **HGGC 驱动程序**：可视为 PPU 的操作系统。是安装在宿主系统 OS 上的软件组件，对 PPU 的所有用途都必不可少，是 SAIL 平台的基础。
- **SAIL 工具包（SAIL Toolkit）**：一套包含**库、头文件和工具**的集合，用于编写、构建和分析利用 PPU 计算能力的软件；是独立于 HGGC 驱动程序的软件产品。
- **HGGC 运行时（HGGC runtime）**：SAIL 工具包所提供的一系列库中的一个特例。既提供一套 API，也提供一些语言扩展，处理常见任务：
  - 分配内存；
  - 在 PPU 与其他 PPU 或 CPU 之间复制数据；
  - 启动核函数（kernels）。
  其中 API 组件称为 **HGGC 运行时 API**。

#### 1.4.2.1 HGGC 运行时 API 与 HGGC 驱动 API

| 对比项 | HGGC 运行时 API (Runtime API) | HGGC 驱动 API (Driver API) |
|---|---|---|
| 层次 | 上层，**在驱动 API 之上实现** | 更底层，直接由 HGGC 驱动程序提供 |
| 便利性 | 提供**隐式初始化、context 管理、module 管理**，简化设备代码管理 | 需显式管理 |
| 功能覆盖 | 对大多数操作足够 | 能实现所有相同功能，且**某些特定功能仅可通过驱动 API 实现** |

- 应用程序可单独使用其中一套，也可**两套 API 结合交替使用**（详见第 3.1 节"HGGC 底层驱动接口"）。

### 1.4.3 T-Head Instruction eXtension (TIX)

- **TIX**：SAIL 平台中被隐藏的层级，即 T-Head 虚拟指令集架构（ISA），是专为 PPU 设计的**高级汇编语言**。TIX 在实际 PPU 硬件的物理 ISA 之上提供抽象层。
- 使用方式：
  - 用户可通过 **Inline TIX 内联汇编**在 C++ 代码中使用。
  - **当前不支持直接用 TIX 汇编语言独立编写程序**，后续 SDK 版本逐步开放。
- 编译链路：特定领域语言（DSL）及高级语言编译器主要以 **LLVM IR**（未来也可通过 TIX 代码）作为中间表示，随后利用 T-Head 提供的**离线编译工具或即时（JIT）编译工具**转化为可执行的 PPU 二进制代码。
- 意义：SAIL 平台不限于 T-Head 官方工具（如编译器 `hgcc`）支持的语言，还可通过其他语言编程。

### 1.4.4 HGbins and HGFatbins

- **hgbin（HGGC binary）**：高级语言（如 C++）代码编译得到的、适用于物理 PPU 的实际二进制代码。每个 hgbin 针对**特定 ARCH 版本（例如 ppu001/ppu0015）**采用特定二进制格式。
- **hgfatbin（HG Fat Binary）**：涉及 PPU 计算的可执行文件和库二进制文件中同时包含 CPU 代码和 PPU 代码，其中 PPU 代码存储在 hgfatbin 容器中。
  - 一个 hgfatbin 容器可包含针对**多个不同目标平台（不同 PPU 架构）**的 hgbin 代码。
  - 应用构建时可同时包含适用于多种不同 PPU 架构（不同 Arch 版本）的二进制代码——这种能力称为"**混合编译**"：**一次编译，在多个 PPU 支持的 ARCH 上都可执行**。
  - 运行时，PPU 代码加载到特定 PPU 上，系统从 hgfatbin 容器中**自动选取最适合当前 PPU 的那份二进制代码**执行。

比赛关联：交付物若需在多代 PPU（ppu001/ppu0015）上跑，用混合编译（`-arch=ppu_10 -arch=ppu_15`）打 hgfatbin，一份二进制通吃；Inline TIX 是冲击"指令集优化"评分项的入口（如手工排布 MMA/访存指令）。

## 1.5 HGGC 特性概览（本章重点）

- 指南第 1–3 章介绍 HGGC 与 PPU 编程的概念基础（配简单代码示例）；第 4 部分描述具体特性的各节默认读者已掌握第 1–3 章。
- HGGC 特性众多，并非所有特性都适用于每种场景。本节按特性**旨在解决的问题类型**粗略分类排序；一些特性（如 HGGC 图）可同时属于多个类别。

### 1.5.1 提升算子性能指引

以下特性都旨在帮助算子开发者最大化其算子（kernels）的性能。

#### 1.5.1.1 避免线程共享内存冲突

- 共享内存数据应尽量**对齐到 16 字节**。
- 除避免 **bank 冲突**外，还应在**分组（group）之间实现负载均衡**，降低**分组冲突**。
- **ppu001 架构**：
  - 共享内存划分为 **2 个分组（groups）**，**每个分组每拍提供 128 字节吞吐带宽**。
  - 多个线程同时访问同一分组 → 分组冲突 → 请求被**序列化处理**，访问延迟增加。
  - **关键规则：地址间隔为 256 字节（地址相差 256B 的整数倍）的访问会映射到同一分组**，容易造成分组冲突。
    - 例：请求 1 访问地址 0，请求 2 访问地址 256B，请求 3 访问地址 512B——物理上相隔较远，但映射到同一分组，导致冲突。
  - 原文配图说明：分组冲突示意图中 4 个 warp 的请求都进入分组 0；分组 0 的每个颜色框代表 128 字节。
  - 实践准则：避免所有 warp 集中访问同一分组，在两个分组间负载均衡；**若请求地址呈线性连续分布，通常能自然分散到不同分组**，有效避免分组冲突。
- **ppu0015 架构**：共享内存分组数从 **2 组增加到 4 组**，每组内连续地址跨度从 **128 字节扩展到 1024 字节**（分组冲突概率显著降低）。

#### 1.5.1.2 原子操作

- **ppu001**：同 warp 的 32 个线程执行**全局内存原子操作**时，应尽量使访问地址**连续且按 128 字节对齐**。否则性能显著下降：
  - **64 字节访问模式**的性能仅为 128 字节模式的 **1/2**；
  - **32 字节访问模式**的性能降至 128 字节模式的 **1/4**。
- **ppu0015**：已优化，64 字节和 32 字节访问模式的原子性能**与 128 字节模式相当**。

#### 1.5.1.3 小粒度访问

- **ppu001**：全局内存上单条读写指令访问的地址过于分散（例如分布在多个不同的**缓存行（cache line，每行 128 字节）**上）会导致性能下降。应尽量使全局读写访问地址集中，**减少所涉及的 128 字节缓存行数量**。
- **ppu0015**：同样建议访问地址集中，但优化目标变为**减少所涉及的 64 字节块的数量**（即 ppu0015 的访问粒度/缓存行为按 64B 块计）。

#### 1.5.1.4 预取

- **ppu0015 的 load/aiu 指令支持预取提示**，可指定预取粒度为 **{128B, 256B}**：
  - 请求读取 **64 字节**时，实际将 **128 字节**数据预取到**最后一级缓存（LLC）**；
  - 请求读取 **128 字节**时，实际将 **256 字节**数据预取到 LLC。

#### 1.5.1.5 异步指令

- 建议尽可能使用 **AIU（AI accelerator in compute Unit，计算单元内 AI 加速器）**相关的**异步指令**替代同步读写指令。
- 机制与收益：
  - AIU 指令可**直接将数据从设备内存搬运至线程共享内存**（绕过寄存器中转）；
  - **减少指令数量**；
  - 利用**专用硬件模块完成地址计算**，避免使用通用算术指令做地址生成，提升整体执行效率。

#### 1.5.1.6 缓存策略

- PPU 读写指令支持**多种缓存策略选项**。当数据**缺乏时间或空间局部性**、预期不会产生缓存命中时，建议选择**绕过缓存（bypass）**，避免占用宝贵的缓存空间、防止有用数据被提前替换。
- PPU 硬件配备**三级缓存**，**各级缓存的绕过行为可独立控制**。具体配置参考《T-Head SAIL TIX 编程指南》中相关指令的说明文档。

#### 1.5.1.7 低精度运算

- 张量计算核支持的数据格式：
  - **ppu001**：**FP16、BF16**。
  - **ppu0015**：在 FP16/BF16 基础上新增 **FP8**，并率先兼容开放计算项目（OCP）定义的 **MXFP4（Microscaling FP4，微缩放 4 位浮点格式）**。
- 格式细节：
  - **FP8**：两种元素格式 **E4M3** 和 **E5M2**。
  - **MXFP4**：元素格式 **E2M1**；**每 32 个元素共享一个缩放因子**，缩放因子采用 **E8M0** 格式。ppu0015 的 **MMA FP4 指令**可同时接收**两个输入矩阵及其对应的缩放因子**。
- 理论算力提升（相对 FP16）：
  - **FP8：2× FP16**；
  - **FP4：4× FP16**。
- 适用场景：**FP8 适用于模型训练和推理；FP4（含 MXFP4）主要面向推理应用**。

比赛关联（§1.5.1 整体）：这是全章对比赛最直接的一节——
- **量化**：ppu0015 的 FP8（E4M3/E5M2）与 MXFP4 是 W8/W4 量化的硬件底座，FP8 2×、FP4 4× 理论算力直接决定量化收益上限；MXFP4"32 元素共享 E8M0 缩放因子"决定了量化 group size 应取 32 的倍数。
- **kernel 优化**：共享内存按 16B 对齐、避免 256B 间隔同组冲突（ppu001）；GEMM/GEMV 的 tile 设计要对照分组/缓存行参数（ppu001：2 组×128B/拍、128B cache line；ppu0015：4 组×1024B、64B 块）。
- **吞吐**：用 AIU 异步指令做 global→shared 搬运（类似 cp.async），配合预取（64B→128B、128B→256B 到 LLC）掩盖访存延迟；无复用的流式数据（如 KV cache 读一遍即弃）应设 bypass 缓存策略保护 LLC。

### 1.5.2 改善延迟

本节特性的共同目标是**降低某种类型的延迟**（不同特性针对的延迟类型不同）。总体关注**核函数启动层级或更高层级的延迟**，**不涉及核函数内部的 PPU 内存访问延迟**。

#### 1.5.2.1 流有序内存分配器

- **流有序内存分配器**允许程序将 PPU 内存的分配与释放**按顺序编排到一个 HGGC stream 中**。
- API 对比：
  - `hggcMalloc` / `hggcFree`：**立即执行**的分配/释放。
  - `hggcMallocAsync` / `hggcFreeAsync`：将一次内存分配或释放操作**插入到一个 HGGC stream 中**（随 stream 顺序执行）。

#### 1.5.2.2 HGGC 图

- **HGGC 图（HGGC Graph）**：使应用能够指定一系列 HGGC 操作（例如 kernel 启动或内存拷贝）以及这些操作之间的**依赖关系**，从而在 PPU 上高效执行。
- 创建方式：
  1. **stream capture**：将一个 stream 上的操作记录到一个 HGGC 图中（使用 HGGC 流也可获得类似行为，stream capture 正是创建图的机制之一）；
  2. **HGGC graphs API**：直接编程建图。
- 图创建后可**实例化并执行多次**——适合将被重复执行的工作负载。
- 性能收益：
  - **减少调用 HGGC 操作相关的 CPU 启动开销**；
  - 启用**只有提前指定整个工作负载时才可用**的优化。
- 详见第 4.1 节（描述并演示如何使用 HGGC 图）。

比赛关联：decode 阶段每 token 要启动大量小 kernel，CPU 启动开销占比高——用 stream capture 把单步 decode 抓成 HGGC 图反复回放（类 CUDA Graph 思路），是降 TTFT/提吞吐的关键系统级手段；KV cache 的 per-step 分配用 `hggcMallocAsync`/`hggcFreeAsync` 避免同步分配打断流水。

### 1.5.3 功能特性

以下特性的共同点：旨在**启用额外的能力或功能**。

#### 1.5.3.1 扩展 PPU 内存

- **扩展 PPU 内存**：在 **ICN 连接的系统**上可用的特性，使得在 PPU 内能够**高效访问系统中的所有内存**。

#### 1.5.3.2 进程间通信（IPC）

- 对于非常大的计算，常见做法是将**多个 PPU 一起使用**以利用更多内存与计算资源协同解决一个问题。
  - 单系统内（集群术语的"一个节点内"）：可在**单个 host 进程**中使用多个 PPU。
  - 也常见使用**独立 host 进程**（跨单台或多台计算机）。多个进程协同工作时，其间通信称为**进程间通信**。
- **HGGC IPC** 提供了在**不同进程之间共享 PPU 缓冲区**的机制。第 4.6 节解释并演示如何使用 HGGC IPC 协调与通信不同的 host 进程。

### 1.5.4 细粒度控制

#### 1.5.4.1 虚拟内存管理

- 如第 2.4 节所述，系统中**所有 PPU 以及 CPU 内存共享一个统一的虚拟地址空间**。
- 大多数应用可使用 HGGC 提供的**默认内存管理**而无需改变行为。
- **HGGC 驱动 API** 为有需要的场景提供对该虚拟内存空间布局的**高级且细粒度的控制**，主要适用于**控制 PPU 之间共享缓冲区的行为**（包括单个系统内和跨多个系统的共享）。
- "虚拟内存管理"章节覆盖了驱动 API 提供的控制项、工作方式，以及开发者何时可能发现其优势。

平台扩展关联（§1.5.3–1.5.4）：HGGC IPC 面向单机多卡/多进程部署，不属于本次单卡比赛路径；本赛道只使用虚拟内存管理精细控制 KV/Mamba cache 等大缓冲区在单设备地址空间中的布局。
